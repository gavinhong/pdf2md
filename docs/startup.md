# 0.2.1 启动与后台预热

本次优化将桌面窗口显示、任务恢复和模型预热分开。界面先显示初始化状态，后台恢复本地配置及任务，再提前加载本地识别流水线。目标是让用户及时看到程序，并缩短首次点击转换后集中等待模型加载的时间；实际耗时及完整等待成本见本文的正式性能记录，不预设通用加速倍数。

## 初始化与兼容

- 桌面使用 `ApplicationService(..., deferred=True)`。构造阶段不恢复历史任务、不完整读取 Markdown、不校验或加载模型文件；默认构造仍同步恢复，保持命令行及现有服务调用兼容。
- `initialize()` 幂等启动后台恢复。重复调用不重复恢复任务或创建并行预热进程。
- `snapshot()` 增加 `startup`，包含 `state`、`phase`、`error`。状态为 `pending/loading/ready/failed`，阶段说明使用用户可理解的中文；快照不等待后台文件读取和模型工作。
- 恢复完成前，导入、移除、重试、转换、核对保存等修改操作明确拒绝，避免空队列覆盖旧任务。后台恢复先构建临时结果，再短时间提交共享状态。
- 初始化未完成时关闭程序，不把尚未恢复的空队列写回 `tasks.json`；恢复失败也保留原有索引和输出文件。
- 索引 JSON 损坏时明确显示初始化失败，保留原始字节；不会把读取失败当成合法空队列。修复后可重新调用 `initialize()`。

## 本地模型预热

- `snapshot()` 增加 `warmup`，包含 `state`、`phase`、`profile`、`error`，状态同为 `pending/loading/ready/failed`。预热期间仍可使用已恢复的任务列表、查看和核对结果。
- 核心恢复后在本地工作进程准备识别流水线，使用与转换一致的模型、配置及网络限制。界面仅按真实消息显示预热阶段，不用固定延时模拟完成。
- 预热结果携带配置 profile，转换只复用相匹配的已准备流水线；配置变化不能误报为该配置已经准备完毕。
- 核心已就绪而预热仍在进行时，可以开始转换：任务先进入等待队列，待预热结束后交给同一工作进程。取消等待项只取消任务，不终止仍有价值的预热。
- 预热失败提供明确原因及 `retry_warmup()`。重试仍通过后台工作进行，避免界面同步加载模型；重复请求不产生多个竞争的工作进程。
- 重试会在后台重新检查本地模型状态，修复缺失模型后无需重启程序；重试接口本身不等待文件检查。
- 工作请求携带请求标识和工作进程代次；过期的阶段、完成及失败事件不能更新当前预热或转换状态。
- 就绪状态绑定存活的工作进程和代次。空闲进程退出后先重新预热，再运行等待项；不会继续显示旧进程的就绪状态。并发重试原子占用一次准备操作，避免重复请求互相终止新进程。
- 准备操作使用独立 epoch 过滤过期线程的最终成功/失败，工作进程使用 generation 过滤过期消息；就绪时绑定对应 generation，不能只凭相同 profile 复用已退出的进程。
- 「取消当前」在批次刚启动、尚未分配当前任务时，仍取消第一个等待项，避免过早点击丢失取消请求。

## 持久化与退出

只在核心恢复完成后持久化任务。退出时停止后台处理与所属工作进程，避免恢复线程在退出后写回过期快照。预热本身不创建转换结果目录，不生成用户转换任务，也不改写原 PDF 或 Markdown。

恢复索引、核对状态和配置仍沿用 0.2.0 格式，不要求用户迁移数据或重新下载模型。默认同步构造保留原行为；桌面通过新增初始化入口使用延迟加载。

## 验证与基准

独立单元测试使用可控的慢恢复、模拟消息和故障，不加载真实模型。`tests/test_startup.py` 和 `tests/test_worker_coordination.py` 合计 30 项通过（2.01 秒），Ruff 通过。覆盖构造立即返回、快照可响应、幂等初始化、恢复前拒绝修改、损坏索引保留、失败重试、预热后自动转换、不同配置补充预热、取消队列保留预热、取消运行使就绪状态失效、单 IO 所有者与过期消息隔离，以及退出关闭阻塞中的模拟 Pipe。另有 Event 控制的并发重试、批次认领前取消和空闲进程退出回归，确认竞争修复后的行为。

预热与转换协调测试执行真实服务调度和结果发布，以内存 FakeProcess/FakeConnection 代替 OS 进程和模型推理；这证明协议及任务状态行为，不代替真实模型耗时与冻结包验收。

`tests/test_warmup.py` 的 8 项模拟测试通过，覆盖实际转换所用的缓存键、方向模型复用、公式关闭时的配置缓存、失败不缓存为就绪、观测包装恢复和工作协议。RapidDoc 默认规则表格路径会跳过公开 warmup 中的表格实例，适配层因此显式准备扫描表格延迟调用所用的原始 `table_config` 缓存键；同时准备公开语言键和实际批次的 `lang=None` 键，避免预热到不被首次转换复用的实例。

源码服务真实模型探针记录在 `output/qa/startup-real-0.2.1/result.json`：从 `initialize()` 调用开始，核心恢复 0.031 秒，全部识别资源就绪 21.408 秒；预热期间提交的扫描表格任务保持等待，资源就绪后自动转换，转换阶段 8.5 秒，输出 3 个表格和 8 张图片。随后数学扫描页转换 3.8 秒，输出 1 个公式和 1 张图片，工作进程复用为 true。阶段记录包含表格识别模型预热；数量另由各自转换报告确认。

该探针不包含进程创建、Python 模块导入、原生窗口显示或浏览器首屏，因此 0.031 秒不能作为应用启动耗时。两个转换任务使用不同文档，也不能计算为同一文档首次/再次转换的加速比例；正式启动对比见下节。

最终启动基准需区分进程启动至窗口可见、核心恢复完成、模型预热完成、首次转换、同配置再次转换；记录样本、机器负载、冷/热缓存和测试方式。窗口显示更早不等于模型已经可用，后台预热耗时也不应隐藏在转换速度统计之外。

最新微调将初始化中轮询改为 100 ms、初始化请求后立即刷新，并内联关键首屏 CSS；Python 后端与模型未变，前端重建和重新封包后的新包复验已通过。最终采样交替测试版本并记录可用内存和长尾；空历史与合成 100 项×16 MiB 历史分别报告，不混算，新配置目录或首次序列不视为操作系统冷启动。

## 正式性能记录：最新 100 ms 轮询及内联样式版本

最终汇总为 `output/qa/performance-comparison-0.2.1-final.json`。同一台 Windows build 26200，Intel Core i5-10500（6 核、12 线程），物理内存 16,944,168,960 字节（约 15.78 GiB）。使用独立配置和已解压发行程序，先旧后新交替运行；每个进程退出后再启动下一个。只将本程序所属窗口置顶并确认 topmost，Windows 未接受 SetForegroundWindow。没有清理 OS 文件缓存，首次序列不是冷开机。

窗口可见约每 10 ms 采样；基础及模型就绪约每 50 ms 观测，转换完成约每 100 ms 观测，均为观察上界，包含 CDP 连接与轮询影响。下表全部从进程启动计时，单位为秒；FCP 为首次内容绘制，基础就绪为观察到任务恢复可用，模型就绪为后台预热完成，三者不能互换。

启动时可用内存分别为 3489.0/3609.7 MiB。预热把模型准备成本移到点击之前，总耗时包含这段等待；不能只用 19.377→4.033 秒宣称通用转换加速。此单次新版 FCP 反而更慢，也说明四对主表中位数不等于每一次启动。样本不足以给出百分位或所有 PDF 的速度承诺。

早期 formal/matched/paired、微调前及不利观测均保留在 `output/qa/`。旧 formal 启动可用内存仅 1962–2244 MiB，不用于最终主比较；微调前两对没有明显 FCP 收益，旧 `first-conversion-0.2.1.json` 的进程到结果 32.525 秒也保留，不能当成最新包结果。探索性汇总 `performance-comparison-0.2.1.json` 保留原样，最终以 `performance-comparison-0.2.1-final.json` 中列明的各场景为准。

操作系统调度、Defender、WebView2 和文件缓存仍会波动；本次四对空历史、单对合成历史与单对转换只说明本机实测。最终归档文档刷新后，CRC 与非文档 payload 一致性由 `scripts/refresh_package_docs.py` 验收并记入归档旁记录，不在包内文档嵌入最终归档摘要。
